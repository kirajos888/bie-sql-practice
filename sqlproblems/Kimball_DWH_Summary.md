### 📑 Semester 2: Kimball Dimensional Modeling Playbook

Here is your summary of the core Data Warehousing architecture patterns covered in **Semester 2**, formatted for your notes and GitHub repository logs.

---

### 1. Core Architecture: Star Schema vs. Transactional (3NF)

* **Goal of Dimensional Modeling (OLAP):** Optimize for **fast query performance** and **intuitive business reporting**, unlike Transactional databases (OLTP / 3NF) which optimize for fast row writes and zero data duplication.
* **Fact Table:** Sits in the middle of a Star Schema. Contains **foreign keys** to dimension tables and **numeric measures** generated by business events.
* **Dimension Table:** Surrounds the fact table. Contains **descriptive text attributes** (context) used for filtering (`WHERE`), grouping (`GROUP BY`), and labeling.
* **Denormalization:** Dimension tables intentionally keep duplicate text (e.g., storing `city` and `state` inside `dim_fulfillment_center`) to avoid multi-table joins, enabling sub-second query speeds.

---

### 2. The 4-Step Kimball Design Framework

1. **Select the Business Process:** Identify the operational activity to track *(e.g., Customer Returns, Package Deliveries)*.
2. **Declare the Grain:** Define what a **single row** in the fact table represents *(e.g., "One row per return pickup attempt")*.
3. **Identify the Dimensions:** Determine the context attributes *(Who, What, Where, When, Why $\rightarrow$ Customer, Product, Warehouse, Date)*.
4. **Identify the Facts:** Determine the numerical measurements *(e.g., `refund_amount`, `shipping_cost`, `distance_miles`)*.

---

### 3. The 3 Fact Table Types

| Fact Table Type | Grain | Update Behavior | Measure Types | Primary Use Case |
| --- | --- | --- | --- | --- |
| **Transaction** | 1 row per discrete event | **Insert-only** | Fully Additive | POS sales, web clicks |
| **Periodic Snapshot** | 1 row per entity per time period | **Insert-only** (at fixed intervals) | Semi-Additive (Cannot sum over time) | Bank balances, daily inventory levels |
| **Accumulating Snapshot** | 1 row per entire workflow instance | **Update-heavy** | Lag/Duration measures between milestones | Order fulfillment pipeline, loan processing |

---

### 4. Advanced Dimension & Fact Patterns

* **Surrogate Keys (SK):** Unique warehouse-generated integers (`INT`) used as Primary Keys in dimensions. Faster for joins than natural alphanumeric strings and required for tracking history.
* **Slowly Changing Dimensions (SCD Type 2):** Preserves full historical truth when attributes change (e.g., customer address move). Closes out the old row (`is_current = FALSE`, sets `effective_end_date`) and inserts a brand-new row with a new Surrogate Key.
* **Degenerate Dimensions:** Low-cardinality attributes (e.g., `return_reason_code` or `order_number`) stored directly inside the fact table without a separate lookup table.
* **Junk Dimensions:** A single combined dimension table grouping multiple miscellaneous flags/statuses (`is_gift_wrapped`, `payment_method`) to prevent fact table column bloat.
* **Factless Fact Tables:** A fact table containing **only foreign keys** and no numeric measures. Used to track event occurrences (*Attendance*) or coverage eligibility (*Promotions*).

---

### 5. Production SQL & BIE Execution Rules

* **`dim_date` Lookup:** Filter on pre-computed integer date attributes (`d.year = 2026 AND d.quarter = 2`) instead of wrapping fact table timestamps in `DATE_TRUNC()`. This enables zone-map pruning in columnar databases like Redshift.
* **Time Differences:** Compute total elapsed hours using `EXTRACT(EPOCH FROM (end_timestamp - start_timestamp)) / 3600.0` rather than `EXTRACT('hours' FROM ...)`.
* **Tie-Breaks & Ranking:** Use `DENSE_RANK() OVER (...)` inside CTEs instead of `LIMIT N` when handling tied values at rank boundaries or ranking within groups (`PARTITION BY`).
